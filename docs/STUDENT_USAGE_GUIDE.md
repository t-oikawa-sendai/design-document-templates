## 1. このガイドでできること

目的文は、[管理用要求定義書](./design/01_REQUEST_DEFINITION.md#51-background-and-purpose背景課題目的) §5.1からの引用です。

> SDD（仕様駆動開発）で、AIが作成する設計文書を決まった7文書・決まった節へ収め、重複と冗長化を防ぐためのテンプレートを配布する。生徒は自分のリポジトリに配置して使う。

SDD（Spec-Driven Development／仕様駆動開発）は、先に仕様を定め、その仕様に従ってAIに実装させる進め方です。設計内容と承認は、そのリポジトリの持ち主が判断します。AIに未決事項や承認実績を推測で埋めさせず、持ち主が確認します。

流れは「取得 → 配置 → 自分の文書として初期化 → 記入と確認 → 仕様変更と実装」です。基本構成は `docs/design/README.md` と 01〜06 の7文書です。AGENTS.md と CONSTITUTION.md は利用先で任意であり、両方なくても記入、仕様変更、実装、確認を進められます。

7文書を置いただけでは効果は保証されません。記載する節を指定し、同じ内容は再掲せず正本を参照し（SSOT）、人が内容を確認します。設定ファイルが既にある場合は、その現行ルールを読みます。設定を削除したり無視したりして、別の運用へ移す案内はしません。

配布元自身の管理ルールと、利用先で設定が任意であることは別です。設定を任意で導入する手順は [7文書管理と設定ファイルの参考資料](./GOVERNED_DEVELOPMENT_GUIDE.md) を参照してください。

## 3. 7文書の役割

| ファイル | 文書ID | 答える問い | 記載例 |
|---|---|---|---|
| `README.md`（設計書フォルダ内） | `README-001` | 全体として何を作るか | 概要・設計書一覧・全体方針。詳細は個別文書へ案内。 |
| `01_REQUEST_DEFINITION.md` | `REQ-001` | なぜ、誰のために作るか | 背景・要求・利用者の要求・制約・成功条件。 |
| `02_REQUIREMENTS_DEFINITION.md` | `REQS-001` | システムは何を満たすか | 機能・性能などの条件・要求との対応。 |
| `03_DATA_AND_SECURITY_DESIGN.md` | `DATA-001` | データを誰がどう扱うか | データの関係・保存方法・権限・安全性。 |
| `04_UI_AND_FLOW_DESIGN.md` | `UI-001` | どの画面でどう操作するか | 画面項目・画面遷移・入力確認・操作の流れ。 |
| `05_ARCHITECTURE_DESIGN.md` | `ARCH-001` | どの構成で実現するか | 構成図・採用技術と理由・API・環境・障害対策。 |
| `06_OPERATION_AND_HANDOFF.md` | `OPS-001` | どう確認して引き継ぐか | テスト方針・受け入れ基準・公開や障害対応の方針。 |

例えば「ログインした利用者だけが自分の記録を見られる」という条件は02、権限や保存方法は03、画面と操作は04、構成とAPIは05、確認するテストは06へ書きます。同じ条件を別々に決め直さず、正本の節を参照します。

01で目的、02で必要な機能、03〜05で具体的な設計、06で確認・引き継ぎ方法を整理します。設計書READMEの一覧も、記入に合わせて更新します。

各文書の節の構成は、テンプレート冒頭の目次（Table of Contents）を参照します。節一覧は転記しません。

## 4. 取得と配置

取得方法は次のとおりです。

1. 配布リポジトリを開きます。
2. Code を開き、Download ZIP を選びます。
3. ZIPを展開します。
4. `templates/design/` の7ファイルだけを、自分の `docs/design/` へコピーします。
5. [§5](#5-自分の文書にする) で初期化します。

展開した配布リポジトリの中で、自分の開発を始めないでください。既存の文書がある場合は、上書きする前にバックアップし、差分を確認します。この配布リポジトリは現在 Private です。公開後に取得する手順とは別です。

取得元は `templates/design/` です。次の7文書をセットで取得し、自分のプロジェクトの `docs/design/` へ置きます。配布元の `docs/design/` は配布リポジトリ自体の設計です。自分の設計書としてコピーしません。

## 5. 自分の文書にする

7文書の冒頭にある文書情報を、次の値で初期化します。

| 項目 | 初期値 |
|---|---|
| Document ID（文書ID） | テンプレートの既存IDを維持する。対応は§3の表。 |
| Owner（管理者） | 自分の名前。 |
| Created Date（作成日） | 自分の文書として初期化した日。`YYYY-MM-DD` 形式。 |
| Last Updated（最終更新日） | 初期化した日。その後は実際に更新した日。 |
| Version（バージョン） | `0.1`。配布テンプレートの版数とは別に、自分の初版を開始する。 |
| Status（ステータス） | `Draft`。 |

設計書READMEの一覧も、個別文書のVersion・Status・Ownerに合わせます。`（記入欄）` を自分の情報へ置き換え、未決の内容は「未決」と分かるように残します。

`0.x` は草稿、`1.0` は初回承認版です。承認は、リポジトリの持ち主が内容を確認して行います。AIが記入しただけで `Approved` にはしません。すべての未決事項を解消しなければ確認できない、という条件はありません。

承認前に、次を確認します。

1. 未決の内容と決定済みの内容が区別されていること。
2. 同じ仕様を複数の節で独立管理していないこと。
3. 未記入欄の有無を確認し、対象外には理由、未決には未決事項への参照があること。
4. 01の成功基準、02の対応要件、設計、06のテスト・確認方法がつながっていること。
5. 未決の内容を確定仕様として実装する指示がないこと。

当該の未決仕様は、決定し、設計へ反映し、確認したあとで実装します。

リンクと画像も自分の内容に合わせます。テンプレートの `../../CHANGELOG.md` は、自分のプロジェクトの変更履歴への相対リンクです。変更履歴の文書を使わない場合は、自分のコピーの該当箇所に「この文書では履歴文書を使用しない」と記載し、存在しないリンクを残しません。配布元の履歴を自分の履歴として代用しません。

画像パスは記入例です。自分の画像を用意して参照先を直すか、使わない場合は該当しない理由を記載します。代表画像は `docs/design/screenshots/thumbnail/`、詳細画像は `docs/design/screenshots/full/` が配置例です。リンク先を実際に開き、図が表示されるか確認してください。

これらは自分の `docs/design/` の記入です。配布元のテンプレートを修正する作業とは異なります。該当しない節は、持ち主が確認したうえで対象外の理由を記載します。

## 6. AIへの指示

管理方式は、設定ファイルの有無で変わりません。仕様の正本は設計7文書です。AGENTS.md と CONSTITUTION.md がなくても、次の指示で開始できます。設定がある場合は、その現行ルールも読み、7文書を省きません。構成と適用方法は [参考資料の共通前提](./GOVERNED_DEVELOPMENT_GUIDE.md#管理方式の共通前提) を参照してください。使用するAIへ対象ファイルを指定し、読めた文書と版を確認します。新しい会話や別のAIへ切り替えるときも、最新のファイルと今回の対象を渡します。任意の設定導入は [7文書管理と設定ファイルの参考資料](./GOVERNED_DEVELOPMENT_GUIDE.md) を参照してください。

`<...>` を自分の情報へ置き換えて使います。

### Document Writing（AIに文書を書かせる）

```text
対象リポジトリ：<自分のRepository URLまたは名前>
最新のdocs/design/README.mdと01〜06を読み、読めた文書と版を示してください。
今回は<文書パス・節>だけに<記入内容>を書いてください。
新しい設計文書を作らず、テンプレートのコメント（<!-- -->）に従ってください。
同じ内容を再掲せず、正本の文書・節を参照してください。
不明な仕様は私に確認し、他の節への影響は変更候補として示してください。
```

### Specification Change（仕様を変える）

```text
対象リポジトリ：<自分のRepository URLまたは名前>
変更内容：<変更したい仕様>
最新の設計7文書から影響する文書と節を確認してください。
先に該当設計書を更新し、重複を増やさず参照関係を整えてください。
私が設計変更を承認した後、その仕様に従って実装と関連テストを更新してください。
```

### Implementation（実装させる）

```text
対象リポジトリ：<自分のRepository URLまたは名前>
今回の実装：<機能と変更可能な範囲>
基準設計書：<パス・節・版>
該当設計書を読み、その仕様に従って実装してください。
設計書にない仕様を追加せず、不足や矛盾は私に確認してください。
変更差分と検証結果、未確認事項を示してください。
```

案や差分を読み、自分の判断と合っているか確認します。決めた内容だけを反映します。承認前の確認項目は [§5](#5-自分の文書にする) を参照してください。次回のために、決めたこと・未決のこと・次に扱う節をメモしておきます。

## 7. Frequently Asked Questions（よくある質問）

### Q1. How Do I Start?（既存の設計書がある場合・これから設計する場合はどう始めますか？）

**A.** 既存の設計内容を7文書の該当する節へ整理し、確認後に7文書を設計文書の正本にします。

7文書の取得と配置は[§4](#4-取得と配置)、初期化は[§5](#5-自分の文書にする)を参照してください。

#### Existing Design Documents（既存の設計書がある場合）

1. 既存の設計書と作業先の7文書をバックアップします。
2. AIに7文書と既存の設計書を読み込ませ、次の指示を渡します。

   ```text
   対象リポジトリ：<自分のリポジトリURLまたは名前>
   既存の設計内容を、7文書の該当する節へ整理して転記してください。
   テンプレートのコメントの指示に従ってください。
   新しい設計文書を作らず、同じ内容は正本の節に書き、他の節では参照してください。
   元の文書は変更・削除しないでください。
   不明点・矛盾・転記先が決められない内容は、対応する文書の未決事項に記録してください。
   仕様や承認実績を推測で補わないでください。
   転記元と転記先、未決事項を作業結果として示してください。
   ```

3. 転記漏れ、意味の変更、矛盾、重複がないか確認し、リポジトリの持ち主が内容を承認します。未決事項は未決のまま明示します。
4. 次の指示で、確認済みの7文書を設計文書の正本に切り替えます。

   ```text
   対象リポジトリ：<自分のリポジトリURLまたは名前>
   これ以降は、docs/design/の7文書を設計文書のSSOT（唯一の正本）として扱ってください。
   旧設計書は移行前の資料として参照し、新しい仕様の正本にはしないでください。
   仕様変更は先に7文書の該当する節へ反映し、確認後に実装してください。
   未決事項を確定仕様として実装しないでください。
   ```

5. 旧設計書に「移行前の資料」と明記して保管し、設計変更は7文書へ反映します。

#### New Design or Outline（これから設計する場合・アウトラインがある場合）

1. 概要設計書や設計メモがあればバックアップし、7文書とともにAIへ読み込ませます。
2. 次の指示を渡します。メモがない場合は、分かっている目的や要求を伝えます。

   ```text
   対象リポジトリ：<自分のリポジトリURLまたは名前>
   これからは、docs/design/の7文書を設計文書のSSOTとして扱ってください。
   概要設計書や設計メモがある場合は、7文書の該当する節へ整理して転記してください。
   元の資料は変更・削除しないでください。
   テンプレートのコメントに従い、同じ内容を再掲せず正本の節を参照してください。
   不明点は未決事項として記録し、仕様や承認実績を推測で補わないでください。
   ```

3. 内容を確認し、リポジトリの持ち主が承認します。AIへの文書作成・仕様変更・実装の指示は[§6](#6-aiへの指示)を参照してください。

### Q2. Are Configuration Files Required?（7文書以外に設定ファイルは必要ですか？）

**A.** 必須ではなく、7文書だけでも運用できます。

同じ管理方式を設定の有無でAIへ適用する方法は、[参考資料の共通前提](./GOVERNED_DEVELOPMENT_GUIDE.md#管理方式の共通前提)を参照してください。
メリット、デメリット、導入方法は、[参考資料§2以降](./GOVERNED_DEVELOPMENT_GUIDE.md#2-設定なしの使用方法)を参照してください。

### Q3. What Happens Without Configuration Files?（設定ファイルがない場合はどう動きますか？）

**A.** 7文書の管理ルールが自動で適用されるとは限らないため、必要な文書と指示をAIへ渡します。

[§6](#6-aiへの指示)の開始指示を使い、AIが対象の7文書を読んだことと、作業結果が指示に沿っていることを確認してください。
既存の設定ファイルやプロジェクト指示がある場合は、その適用範囲を確認し、既存ルールに従ってください。

### Q4. Are the Seven Documents Read Automatically?（7文書は自動で読み込まれますか？）

**A.** 自動読込みへの対応は、使用するAI・ツールと設定によって異なります。

ファイルを置くだけで7文書すべてが自動で読み込まれるとは限りません。
Gemini、ChatGPT、ClaudeのWeb版・Desktop版の対応、公式情報のURL、確認日は[参考資料§8](./GOVERNED_DEVELOPMENT_GUIDE.md#8-使用するaiごとの設定方法と公式情報)を参照してください。
文書の更新後は最新の7文書を読み込ませ、読み込まれた対象を確認してください。

### Q5. How Do I Handle Undecided Items?（未決事項はどう記入しますか？）

**A.** 推測で確定させず、対応する設計文書の未決事項へ記録します。

文書IDと未決事項IDの組で識別し、他の文書からはその項目を参照します。
既存の課題台帳がある場合は、その識別子を参照し、同じ課題を二重に登録しません。
決定内容は持ち主が確認し、設計書へ反映してから当該仕様の実装へ進みます。

### Q6. How Do I Update Templates?（新しいテンプレートへ更新するときはどうしますか？）

**A.** 記入済みの7文書をバックアップし、新旧の差分を確認して必要な変更を反映します。

新しいテンプレートで記入済み文書をそのまま上書きしないでください。
記入欄や指示コメントの変更を確認し、既存の設計内容、参照関係、メタ情報を保ったまま更新します。
作業後は欠落・矛盾・重複を確認し、リポジトリの持ち主が内容を確認します。
