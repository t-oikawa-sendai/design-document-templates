本書は、7文書の記載先と、設定ファイルを任意で使う方法を説明する参考資料である。削除したり別の場所へ移したりせず、この配布物の一部として置く。基本の記入・仕様変更・実装は [使用説明書](./STUDENT_USAGE_GUIDE.md) だけで始められる。非公開の原本を読めなくても、その基本の運用は成立する。

製品がファイルを自動で読むとは扱わない。使用するAIへ読むファイルを指定し、読めたパスと版を確認する。

## 1. 7文書の記載先とSSOT

SSOTは、正しい情報の管理元を一つに定める原則である。同じ仕様を複数の文書で決め直さず、正本を一つにする。他の文書はその正本の文書・節を参照する。

基本構成は `docs/design/README.md` と 01〜06 の7文書である。新しい設計文書を増やして似た説明を並べない。変更するときは、影響する文書と節を確認し、参照関係を崩さない。7文書があるだけでは効果は保証されない。記載先の指定、参照の維持、人による確認を続ける。

## 2. 設定なしの使用方法

1. `templates/design/` の7文書を、自分の `docs/design/` へ配置する。配布元の `docs/design/` はコピーしない。
2. 使用説明書の初期値で文書情報を初期化する。
3. 使用説明書の指示例を、今回の作業に合わせてAIへ渡す。
4. 新しい会話や別のAIへ切り替えるときも、最新の7文書と、対象・作業範囲を渡す。

AGENTS.md と CONSTITUTION.md が無いことは、不足でも停止理由でもない。設定が無い場合は、7文書と明示した指示で進める。対象のリポジトリは毎回指定する。

## 3. 設定ありの使用方法

設定ファイルが既にある利用先では、その現行ルールを読む。設定を削除したり無視したりして、設定のない運用へ移さない。

| ファイル | 役割 |
|---|---|
| `AGENTS.md` | AIの作業手順。読む対象と順序、作業の進め方を共通にできる。 |
| `CONSTITUTION.md` | 権限、承認、禁止事項などの共通ルール。仕様を守る作業範囲を共通にできる。 |

設計7文書は、何を作るかの仕様を書く場所である。設定ファイルは、AIがどの順で読み、誰の承認に従うかを書く場所である。役割は異なる。

AIが読んだパスと版、理解した作業範囲を確認する。設定の更新と、設計書との矛盾も点検する。置くだけでは、AIが従うことは保証されない。

配布元自身は、既存の管理ルールで運用を続ける。利用先で設定が任意であることと、配布元の必須の管理資産は別である。

この配布元に置いてある中央管理のコピーには、所有者個人を権限者とする記述がある。設定ファイルをコピーすれば、誰のリポジトリでもそのまま使える、とは扱わない。利用先に適した承認者と導入条件が確認できないコピーを、そのまま導入しない。中央管理コピーの修正は中央原本側の手順が必要であり、本書の作業では行わない。

## 4. 任意導入の手順

導入するかは、利用先リポジトリの持ち主が決める。

1. 持ち主が導入を決める。
2. 導入するルールの適用範囲、承認者、既存ルールとの整合を確認する。確認できない場合は導入しない。
3. 確認できたルールを、リポジトリのルートへ配置する。
4. 使用するAIに、そのファイルを読むよう指定する。
5. 読む順序と、今回の作業範囲の認識を確認する。

## 5. 初期指示と再開指示

開始時と再開時に、設定の有無を確認する。ある場合は既存ルールに従う。ない場合は7文書と明示した指示で進める。対象リポジトリを毎回書く。

初期指示の例:

```text
対象Repository：<自分のRepository URLまたは名前>
このリポジトリに AGENTS.md と CONSTITUTION.md があるか確認してください。
ある場合は、その現行ルールを読み、読む順序と今回の作業範囲を示してください。削除や無視はしないでください。
ない場合は、最新の docs/design/README.md と 01〜06、および今回の作業範囲を読み、設定ファイルの不在を不足として止めないでください。
読めた文書と版、読めなかったものを示してください。
```

再開指示の例:

```text
対象Repository：<自分のRepository URLまたは名前>
作業を再開します。前の会話だけを基準にせず、最新のファイルを読み直してください。
AGENTS.md と CONSTITUTION.md がある場合は、その現行ルールに従ってください。
ない場合は、最新の設計7文書と、今回の対象・作業範囲に従ってください。
何を確認できたか、何が未確認かを区別してください。
```

## 6. 設計変更から実装までの確認

順序は、設計書の変更、持ち主の承認、実装、差分と検証の確認である。文書を書かせる、仕様を変える、実装させる、の具体的な指示例は [使用説明書](./STUDENT_USAGE_GUIDE.md#6-aiへの指示) にある。本書へ全文は再掲しない。

実装のあと、変更差分と検証結果、未確認事項を示させる。差分は Git で確認する。Git は、ファイルの変更履歴を管理する仕組みである。AIの完了報告だけを、確認済みとは扱わない。

## 7. デメリット

- 維持する対象が増える。設定と設計書の両方を更新し、矛盾がないか見る必要がある。
- 古いルールや、互いに矛盾したルールが残ると、AIも人も混乱する。
- ファイルを置いただけでは、遵守は保証されない。読んだことと、従った結果を確認する。

既存の設定を削除することは、これらの改善手段にしない。
